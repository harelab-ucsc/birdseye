# BirdsEye

> **Version note** — This is the v1 (SQLite) line of birdsEye, frozen at tag `v1.0.0` for the manuscript *Human-in-the-Loop Geospatial Annotation for Rapid Dataset Construction in Field-Deployed UAV Systems* ([arXiv:2609.28767](https://arxiv.org/abs/2609.28767)). Active development (3-D ray casting, SE(3)) is on [`main`](https://github.com/harelab-ucsc/birdseye/tree/main). v1 receives bug fixes only.

We have a technical operating manual (under development) available via [this link](https://docs.google.com/document/d/1-FZzE7Eh_Zi3TRnGS_bfW5jOKc4YxBhRKGrLWPVRbck/edit?usp=sharing).

## Annotation system

The annotation system is a 2-stage process in the command line: (i.) the user 
parses the flight dataset from the ROS2-native `bag` file format into a sqlite 
database using the ROS2 node `sub_node`, then (ii.) the user passes the resulting 
database to the script, `birdseye/birdseye.py`, to run the geotag detection and image 
annotation processes.

### i. Parsing from ROS2 to SQLite
First and foremost, the software establishes the following file structure on each
run (deleting the contents of an existing instance, if one is present):
```
~/
|__ parsed_flight/
   |__ flight_data.db
```

Moreover, it assumes the following file structure in the home directory:
```
~/
|__ bE_config/
|  |__ data.csv  // the geotags to be associated with this flight's imagery
|__ ros2_ws/
   |__ build/
   |__ install/
   |  |__ setup.bash
   |__ log/
   |__ src/
      |__ birdseye/ // clone of this repo
      |__ robot_localization/  // clone of git@github.com:cra-ros-pkg/robot_localization.git
```

This step reqires the user to provide the file(s) in the `bE_config` directory. The 
call to the birdsEye ROS2 node, `sub_node`, will require, at minimum, a path to a valid 
ROS2 bag file containing flight data. To run `sub_node`, a user can use the following
command line invokation:
```
source ~/ros2_ws/install/setup.bash
ros2 launch ~/ros2_ws/src/birdseye/launch/legacy/dualEKF_birdseye.launch.py bagpath:=[/path/to/data]
```
This command will take as long as ROS2 takes to play back the flight (can be
accelereated/decelerated w.r.t. real time playback), and will result in the following
file structure in the user's home directory:
```
~/
|__ parsed_flight/
|  |__ flight_data.db  // generated by sub_node's execution
|
|__ bE_config/
|  |__ data.csv  // the geotags to be associated with this flight's imagery
|
|__ ros2_ws/
   |__ build/
   |__ install/
   |  |__ setup.bash
   |
   |__ log/
   |__ src/
      |__ birdseye/  // clone of this repo
      |__ robot_localization/  // clone of git@github.com:cra-ros-pkg/robot_localization.git
```

The full set of arguments exposed at the command line for `launch/legacy/dualEKF_birdseye.launch.py` is
as follows:

`bagpath`: filepath to flight data file. Defaults to a filepath which will never be right. REQUIRED.

`rl_launch_path`: filepath to the `robot_localization` state estimators' ROS2 launch script.
        Defaults to `~/ros2_ws/src/birdseye/launch/dualEKF_navsat_gx5.launch.py`; the file now lives at
        `launch/legacy/dualEKF_navsat_gx5.launch.py`, so pass that path explicitly.
        
`be_launch_path`: filepath to the `sub_node` ROS2 launch script.
        Defaults to `~/ros2_ws/src/birdseye/launch/subNode.launch.py`; the file now lives at
        `launch/legacy/subNode.launch.py`, so pass that path explicitly.

`sensorID`: `sub_node` parameter, designating the ROS2 `frame_id` for the camera associated 
        with this sub_node instance. Defaults to `cam0`.
        
`cam_topic`: `sub_node` parameter, designating the ROS2 topic associated with the imagery
        from the camera associated with this `sub_node` instance. Defaults to 
        `/cam0/rgb_cam/image_raw`.
        
`sensors_yaml`: `sub_node` parameter, designating the filepath to `birdsEyeSensorParams.yaml`.
        Defaults to `~/ros2_ws/src/birdseye/config/birdsEyeSensorParams.yaml`.
        
`clicks_csv`: `sub_node` parameter, designating the filepath to `data.csv`, the file containing
        the geotag data to be associated with this flight's imagery.
        Defaults to a filepath which will never be right, from my laptop. REQUIRED.

## Path planning

The process of generating a new path involves physically collecting 
"clicks" of latitudes/longitudes, then feeding the CSV file generated by the
clicks  into the `birdseye/GPS_path_planner.py` script which generates a KML-formatted
flight plan.

USAGE:
```bash
$ python3 birdseye/GPS_path_planner.py --input=${CSV_IN}.csv --output=${KML_OUT}.kml
```

In the above:
- `${CSV_IN}` is the path to the input "clicks",
- `${KML_OUT}` is the path to the output/drone-readable KML-formatted flight 
plan.


### GPS\_path\_planner.py - Usage

To see the list of available options for this script, type:
```bash
$ python3 birdseye/GPS_path_planner.py --help
```

## Reproducing the manuscript

The pose-uncertainty and design-bound analyses are standalone scripts (NumPy/SciPy/Matplotlib; `design_bound_lp.py` and `design_bound_ablation.py` also need `cvxpy`):

- `scripts/pose_uncertainty_prop.py` — first-order propagation of 6-DOF pose uncertainty to pixel/ground error, with Jacobian validation, perturbation and scaling studies, and ellipse panels. No command-line arguments: run `python3 scripts/pose_uncertainty_prop.py`; it sweeps altitudes 5/10/20/50 m and saves results to `~/catch/uncertainty_prop_<timestamp>.pkl`. The default `std_devs=[0.01, 0.01, 0.06, 0.04, 0.04, 0.13]` (x, y, z in m; roll, pitch, yaw in deg) are the deployed 1σ of manuscript Table 9.
- `scripts/design_bound_lp.py` — trace-based certified design bound and design heuristic (admissible per-DOF 1σ pose accuracy vs. altitude and pixel fidelity). `python3 scripts/design_bound_lp.py [--altitudes A ...] [--lam-target L] [--stride S] [--std-devs 6×σ] [--rho-max R] [--radii R ...] [--z Z] [--out PDF] [--json JSON] [--pdf] [--render STUDY_JSON] [--self-test]`. Defaults: altitudes 5 10 20 50, `--lam-target 100`, `--std-devs 0.01 0.01 0.06 0.04 0.04 0.13`, `--out ~/catch/design_bound_lp.pdf`; the PDF is rendered only with `--pdf` (or from a saved study with `--render`).
- `scripts/design_bound_ablation.py` — normalization ablation (solve coordinates × objective units) for `design_bound_lp.py`. `python3 scripts/design_bound_ablation.py [--altitudes A ...] [--stride S] [--lam-target L] [--std-devs 6×σ] [--rho-max R] [--repeats N] [--z Z] [--json JSON]`. Defaults: altitudes 10 20, `--stride 4`, `--repeats 5`, `--json ~/catch/design_bound_ablation.json`.
- `scripts/flat_world_test.py` — Monte-Carlo flat-world projection error vs. terrain decline angle at 1/10/20 m. No command-line arguments: `python3 scripts/flat_world_test.py`; reads `config/birdsEyeSensorParams.yaml` (`cam0`) and saves contour plots to the hard-coded directory `/home/mwmaster/catch/` (edit the `savefig` path before running elsewhere).

Tables 4–9 and the in-text statistics of the manuscript were generated from the field datasets by the authors' analysis pipeline (`manuscript_numbers.py`), which is not part of this repository; it and the raw data are available from the corresponding author on request.

## Additional tools

- `birdseye/clicks2geojson.py` — converts Clicker CSV output (`latitude, longitude, altitude_wgs, altitude_wsl, gps_status, label`) to GeoJSON for QGIS / OASIS Sim: `from birdseye.clicks2geojson import write_clicks2geojson; write_clicks2geojson("clicks.csv", "clicks.geojson")`. Running the file directly executes its self-test.
- `scripts/ortho.py` — stitches aerial images into an orthophoto at a fixed projection depth: `python3 scripts/ortho.py --images_dir DIR --poses_json POSES.json --intrinsics_yaml INTRINSICS.yaml --depth D [--resolution 0.1] [--output orthophoto.png]`.
- `scripts/grid_flight.py` — adds grid waypoints inside the convex hull of a set of geotag clicks and writes clicks + grid points as a flight-plan CSV: `python3 scripts/grid_flight.py -c CLICKS.csv -p PLAN.csv`.
- `birdseye/synthetic_db.py` — ROS 2 node that builds a synthetic `flight_data.db` from scripted UAV poses (via `dbConnector`) for exercising the v1 pipeline without a flight. It has no `console_scripts` entry; call `birdseye.synthetic_db.main()` from a sourced ROS 2 environment.
